# Sprint NN — Sprint Name

## 1. Status

- **State:** Planned, active, implemented, or accepted
- **Stage:** Roadmap stage
- **Primary owner:** Product owner
- **Implementation:** Assigned implementation agent
- **Depends on:** Required prior outcome
- **Blocks:** Dependent future sprint or outcome

## 2. Primary outcome

State one observable outcome that defines the sprint.

## 3. User story

As a specific user, I want a specific capability so that I receive a specific benefit.

## 4. Starting state

Describe the verified repository and product state at activation, including known limitations.

## 5. Included scope

- List only approved capabilities required for the primary outcome.

## 6. Excluded scope

- List tempting adjacent capabilities that remain unauthorized.

## 7. Functional requirements

### FR-01 — Requirement name

Describe the observable behavior and error handling.

## 8. Technical requirements

### TR-01 — Requirement name

Describe the required architecture, contracts, integrity rules, or tooling.

## 9. Domain contracts and assumptions

Define authoritative domain entities, formulas, timing, prices, units, costs, precision, rounding, and unsupported behavior.

## 10. UX states

Describe initial, active, completed, loading, empty, disabled, and error states as applicable.

## 11. Acceptance criteria

- [ ] Each item must be observable and have pass/fail evidence.
- [ ] Included scope is complete and excluded scope was not introduced.

## 12. Automated test minimum

### Domain

- Formula and precision cases.
- Valid and invalid state transitions.
- Boundary and failure cases.

### Integration

- Critical user flow and relevant API contracts.

## 13. Manual verification

1. Start from a clean documented setup.
2. Exercise the primary user flow.
3. Verify calculations independently where applicable.
4. Verify errors, accessibility, and responsive behavior.

## 14. Documentation updates

- [ ] Update `docs/STATUS.md`.
- [ ] Update this sprint's evidence and checklist.
- [ ] Record material decisions in `docs/DECISIONS.md`.
- [ ] Update setup, API, or schema documentation where behavior changed.
- [ ] Add an immutable action summary under `docs/summaries/`.

## 15. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Describe a material risk | Describe the consequence | Describe the control and evidence |

## 16. Sprint completion evidence

To be completed only after implementation and verification:

- Repository state before work:
- Files created or modified:
- Decisions recorded:
- Commands run:
- Automated test results:
- Production build result:
- Manual verification results:
- Remaining limitations:
- Documentation updated:
- Review decision:

Do not mark the sprint accepted until the product owner explicitly accepts the completed outcome.
