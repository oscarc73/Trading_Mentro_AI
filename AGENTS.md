# AGENTS.md — Trading Mentor AI

This file defines the durable operating instructions for every coding agent working in this repository.

## 1. Mandatory reading order

Before changing code, read:

1. `AGENTS.md`
2. `docs/PROJECT_MASTER.md`
3. `docs/ROADMAP.md`
4. `docs/STATUS.md`
5. `docs/ENGINEERING_RULES.md`
6. `docs/CODEX_WORKFLOW.md`
7. The active sprint file referenced by `docs/STATUS.md`
8. Any README or local `AGENTS.md` in the directory being modified

Do not start implementation until the repository and active scope have been inspected.

## 2. Mission

Build Trading Mentor AI as a reliable educational trading simulator and strategy-research platform. The initial product must use historical or simulated data and must not execute real-money trades.

## 3. Working rules

- Work only on the active sprint or explicitly assigned task.
- Do not add speculative features, abstractions, services, or dependencies.
- Prefer the smallest coherent change that fully satisfies acceptance criteria.
- Preserve existing behavior unless the task explicitly changes it.
- Never claim completion without running the required checks.
- If the repository state conflicts with documentation, report the conflict and update documentation only when evidence supports the change.
- Do not silently weaken tests, validation, typing, security, or financial correctness.
- Never commit credentials, API keys, secrets, private data, or `.env` files.
- Do not integrate broker execution or real-money trading during the initial 10-sprint roadmap.

## 4. Initial technical direction

Use the following unless an approved decision record changes them:

- Monorepo.
- Web: Next.js, React, TypeScript.
- UI: Tailwind CSS and accessible reusable components.
- Charting: TradingView Lightweight Charts or an approved equivalent.
- API/data services: Python with FastAPI.
- Initial storage: local files and SQLite where persistence is required.
- Package manager for JavaScript: pnpm.
- Python environment and dependency tooling must be documented in the repository once selected.
- Time values: UTC internally; format for the user's locale only at presentation boundaries.

Do not pin arbitrary versions in documentation. Use versions present in lockfiles and record material upgrades in `docs/DECISIONS.md`.

## 5. Financial and market-data correctness

- Treat OHLCV data as untrusted input and validate schema, ordering, duplicates, gaps, timestamps, numeric ranges, and candle consistency.
- Never expose future candles to simulation logic before their simulated time.
- Entry and exit prices must be generated by explicit execution rules.
- P&L formulas must be centralized and tested for long and short positions.
- Fees, slippage, spread, leverage, and position sizing must never be hidden. If not implemented, show zero/default assumptions explicitly.
- Use decimal-safe calculations for money and quantities when precision matters.
- Separate educational explanations from deterministic engine calculations.
- Backtest and simulated performance must be labeled as hypothetical.

## 6. Code quality

- Type all public interfaces.
- Keep domain logic independent from UI components.
- Avoid duplicated P&L, order, candle, or position calculations.
- Use clear domain names: `Candle`, `Order`, `Position`, `Trade`, `SimulationSession`, `ExecutionFill`.
- Validate at system boundaries.
- Write tests for every financial formula, state transition, and bug fix.
- Prefer explicit state machines or reducers for trading-session transitions.
- Add comments only where intent or a non-obvious constraint cannot be expressed by naming and structure.

## 7. Required checks

Before reporting completion, run the commands available in the repository for:

- install/dependency consistency
- formatting
- lint
- typecheck
- unit tests
- integration tests when applicable
- production build

If a command does not exist yet and the active sprint requires it, create and document it. If a check cannot run, state exactly why and do not mark it as passed.

## 8. Documentation updates

Every completed task must evaluate whether to update:

- `docs/STATUS.md`
- the active sprint file
- `docs/DECISIONS.md`
- a dated action record in `docs/summaries/`
- the relevant README
- API/schema documentation

Documentation must describe the repository as it actually exists, not as intended future work.

Action summaries must follow `docs/summaries/README.md` and record the outcome, files affected, decisions, verification, limitations, and documentation changes. Create one summary for each completed project action; do not rewrite older summaries when later work changes the repository.

## 9. Completion report

Return a concise report with:

1. What changed.
2. Files created or modified.
3. Architecture or product decisions.
4. Commands run and their results.
5. Manual verification performed.
6. Remaining limitations or risks.
7. Documentation updated.

Do not begin the next sprint unless explicitly instructed.
